# Учёт «кто принял оплату» и подмена менеджеров (отпуск/больничный)

## Context

Сейчас оплата по договору может быть проведена не тем менеджером, который ведёт договор (клиент пришёл в другой офис, или менеджер в отпуске/на больничном). Проблемы:
- **ДП (журнал денег)**: движение атрибутируется только менеджеру-владельцу (`MoneyMovement.managerId`), касса/инкассация считается по нему же — хотя физически деньги принял другой сотрудник. `ContractDocumentPackagePayment.recordedById` («Кто внёс») уже пишется из JWT, но в ДП никак не видно и на кассу не влияет.
- **ЗП**: начисление всегда идёт менеджеру договора (`SalaryContract.managerId`), механизма передачи начислений на период отпуска/больничного нет.

Решение — два режима:
- **A. «Принял другой»**: фиксируем сотрудника, принявшего оплату. В ДП — новая колонка «Принял оплату»; его касса (инкассация) — по этому сотруднику; з/п полностью остаётся менеджеру-владельцу.
- **B. «Подмена» (отпуск/больничный)**: супер-админ вручную создаёт подмену «кого → кем → период» (все договоры отсутствующего менеджера). В период подмены: з/п по этим договорам (заключение/закрытие/Д/с, план продаж) и личные продажи/премии по платежам ДП (места по продажам, «QR + Н») начисляются подменяющему; такие оплаты/договоры помечаются бейджами.

Существующая инфраструктура, которую переиспользуем: `recordedById` на оплатах, паттерн `managerId`+`submitterId` инкассации, паттерн супер-админского CRUD периодов `WorkDayLeave`, singleton-настройки ЗП.

---

## 1. БД (Prisma + миграции)

**`backend/prisma/schema.prisma`:**
- `MoneyMovement`: + `acceptedById String?` (кто принял оплату; для авто-записей = `payment.recordedById`) и денормализованный `cashHolderId String?` (чьи наличные: `acceptedById ?? managerId` — единая точка для всех запросов кассы) + отношения к `User` («MoneyMovementAcceptedBy», «MoneyMovementCashHolder», `SetNull`) + индексы.
- Новая модель `ManagerSubstitution` (по образцу `WorkDayLeave`): `absentManagerId` (кого подменяют), `substituteManagerId` (кто подменяет), `dateFrom/dateTo @db.Date`, `comment`, `createdById`, timestamps, индексы по менеджерам и датам.
- `User`: + обратные relations.

**Миграции** (`backend/prisma/migrations/`, шаблон `YYYYMMDDHHMMSS_name`):
1. `..._money_movement_acceptor`: `ALTER TABLE` добавить колонки; backfill `acceptedById` из `contract_document_package_payments.recorded_by_id` (join по `sourceId`); **`cashHolderId = managerId`** (текущие кассы/остатки не меняются — никаких накладок при деплое; на acceptor касса переводится только для новых оплат); FK + индексы.
2. `..._manager_substitutions`: создание таблицы + FK (Cascade по менеджерам, SetNull по createdBy).

## 2. Backend: оплаты и ДП

- **`backend/src/admin/contract-document-packages/dto/payments/*`**: в create-DTO опциональное `acceptedByUserId` (по умолчанию текущий JWT-пользователь; для случая «запись вносит владелец, а принял другой»); в update-DTO (правит только SA — уже так) тоже. `recordedById` = «кто принял/провёл оплату».
- **`.../payments/contract-document-package-payments.service.ts`**: `create()` — `recordedById = dto.acceptedByUserId ?? req-пользователь` с проверкой существования пользователя; `update()` — поддержка смены акцептора.
- **`backend/src/admin/money-movements/money-movements.service.ts`**:
  - `recordFromPackagePayment` / `syncFromPackagePayment`: проставлять `acceptedById` и `cashHolderId` (для CASH-логики).
  - `findAll`: include `acceptedBy`; грузить активные подмены (прямой prisma-запрос, без межмодульной зависимости) и добавлять к строкам `acceptedBy {id,name}`, `acceptedByOther: boolean`, `substitution` (данные бейджа «подмена» для акцептора в период подмены менеджера-владельца); `managerSums`/`directionManagerSums` — при активной подмене продажи засчитываются подменяющему (замена `groupBy` на `findMany` + JS-ремап по `paymentDate`); в `balanceManagerIds` добавить держателей кассы.
- **`money-movement-serialize.ts`**: + `acceptedBy`.
- **`backend/src/admin/money-movements/manager-incassations.service.ts`**: в `getCashBalances` и `cashLedger` запросы движений CASH по `managerId` → по `cashHolderId` (инкассации остаются по `managerId`). Итого: B, принявший наличные по договору A, сдаёт их как свою обычная инкассация; «за кого» (`onBehalfOfId`) остаётся для прочих случаев.

## 3. Backend: подмены + ЗП

- **Новый `backend/src/admin/salary/manager-substitutions/`** (controller + service + DTO, регистрация в `salary.module.ts`):
  - `GET /admin/salary/manager-substitutions` — список (роли раздела ЗП); `GET .../active?managerId=` — активные/будущие подмены менеджера (для баннера в хабе, `CRM_ROLES`).
  - `POST/PATCH/DELETE` — только `@Roles('SUPER_ADMIN')` (паттерн `work-days.controller.ts` / `RolesGuard`).
  - Валидация: пользователи существуют, `absent ≠ substitute`, `dateTo ≥ dateFrom`, запрет пересечения периодов подмен у одного отсутствующего.
- **`salary-calculation.service.ts`**: загрузить подмены, пересекающие период; пост-обработка строк (в строках уже есть `parts: {sign, close, extra}` и даты событий): атрибуция по-частям — sign по `signDate`, close по `closedAt`, extra по датам счетов; правило: активная подмена менеджера-владельца на дату события → часть уходит подменяющему. Строка получает `creditedManagers: [{userId, userName, amount, substitutedForName?}]` и флаг `substitutionApplied` (бейдж). `byManager` строится из `creditedManagers` → `employeeTotals` согласованы автоматически. `SalaryContract.managerId` НЕ переписывается (подмена — слой расчёта, история и обратимость сохраняются).
- **`salary-bonuses.service.ts`**: `monthSalesByManager` (места по продажам) и «QR + Н» — те же findMany + ремап по дате платежа; `managerPartsByMonth` (план продаж) — ремап по дате части.
- **`salary-my.service.ts`**: фильтр «Моя з/п» по `creditedManagers` (подменяющий видит чужие договоры с пометкой, у отсутствующего они пропадают).

## 4. Frontend

- **`frontend/src/shared/api/crm/admin-money-movements.ts`**, **`admin-salary.ts`** (типы + CRUD подмен), **`admin-contract-document-packages.ts`** (`acceptedByUserId` в input оплаты).
- **ДП `MoneyMovementsPageView.tsx`**: колонка «Принял оплату» (после «Менеджер»): имя акцептора, бейдж «подмена» в режиме B, нейтральная отметка — если акцептор ≠ менеджер без подмены (режим A).
- **Хаб «Оплаты и Управление договором»**:
  - форма проведения (`PackageContractPaymentsConductFormSection.tsx` + `usePackagePaymentsConduct.ts`): селект «Принял оплату» (по умолчанию текущий пользователь; источник списка — как в `IncassationModal`);
  - SA-модалка правки оплаты: возможность скорректировать акцептора;
  - баннер в блоке оплат при активной подмене менеджера договора («до {date} за {A} отвечает {B}: оплаты/з/п — за {B}»).
- **ЗП**: в SA-вкладке «Настройки» (`SalarySettingsView`) блок «Подмены менеджеров» — таблица (кого/кем/период/комментарий) + модалка создания/правки; в расчёте (`SalaryCalcView`) бейдж «за {имя} · подмена» у строк, зачисленных подменяющему; в «Моя з/п» — пометка у подменных договоров.

## 5. Что НЕ меняется

- `MoneyMovement.managerId` (менеджер-владелец в колонке «Менеджер», dashboard), `resolveMovementManagerId` и цепочка `signatoryCrmUserId → responsibleManagerId → createdById`.
- З/п замерщика/ВС/бригадира, `managerHandled`, синхронизация `SalaryContract`.
- Ручные проводки ДП: `acceptedById = null`, касса по `managerId`.

## Проверка

1. `cd backend && npx prisma migrate dev --name money_movement_acceptor && npm run build`; вторая миграция аналогично.
2. `cd frontend && npm run build`.
3. Сценарии (при доступном локальном окружении, иначе — прогон API через curl):
   - SA создаёт подмену (A болеет 10–20 числа) в ЗП → Настройки;
   - менеджер B проводит оплату по договору A из хаба → в ДП видна колонка «Принял оплату: B» + бейдж; плитка кассы B пополнилась, A — нет; B сдаёт инкассацию как свою;
   - расчёт ЗП за месяц: строки договора A в период подмены — у B с бейджем «за A (подмена)», вне периода — у A; места по продажам/«QR+Н» учли платежи подмены за B;
   - «Моя з/п» B показывает подменные договоры, у A их нет;
   - без подмены: оплата B по договору A → колонка показывает B, касса B, з/п — A (режим A).
