# Уникальность заказчиков и структурированный адрес

## Контекст
В базе возникли дубли заказчиков (одинаковые ФИО/телефон/адрес), из-за чего расчёт и договор ссылались на разные карточки и вкладка «Смета» не видела расчёт. Корзина (`deletedAt`, `moveToTrash`/`restore`) у Customer уже есть. Адрес хранится одной строкой в `extendedProfile.address` (+ `objectAddresses: string[]`).

## 1. Защита от дублей (блок + подсказка)

**Признак дубля** (проверяется по живым, не удалённым): совпадение нормализованного телефона (по цифрам, по любому из `phones`), или совпадение `email` (регистронезависимо, при наличии), или совпадение полного ФИО (имя+фамилия+отчество, при наличии) **и** телефона.

**Бэкенд**
- `backend/src/admin/customers/customers.service.ts`:
  - новый метод `findPotentialDuplicates(dto)`: `findMany` с `deletedAt: null` по `phones has normalizedPhone` OR `email equalsInsensitive` OR (fullName+phone);
  - в `create()` (строки 129–170) перед вставкой — проверка; при дубле выбрасываем `ConflictException` с payload найденных карточек (id, ФИО, телефоны, email, адрес, менеджер);
  - в `update()` — та же проверка при смене телефонов/email, исключая саму карточку.
- `customers.controller.ts`: `GET /admin/customers/duplicate-check` (query: телефон/email/ФИО) для превалидации из формы на лету/при потере фокуса.
- Нормализацию телефона вынести в общий util (сейчас есть `normalizeCustomerPhones` в сервисе).

**Фронтенд**
- `frontend/src/views/admin/CRM/Customers/shared/crmCustomerFormValidation.ts` + `AddCrmCustomerModal.tsx`: перед отправкой вызываем `duplicate-check`; при найденных дублях — блокируем сохранение и показываем список карточек (ФИО, телефон, email, адрес) с кнопкой «Открыть существующего» (открывает `CrmCustomerDetailModal`) и «Всё равно создать» (повторный запрос с флагом `allowDuplicate: true`, который бэкенд принимает как осознанный обход — так менеджер может создать, например, однофамильца с тем же номером).
- `CrmCustomerSearchPanel.tsx`: при вводе телефона/ФИО, по которым есть совпадение, подсвечивать существующую карточку сверху результатов (поиск уже ищет по `phones has`, дополняем только ранжированием точных совпадений вверх).

## 2. Корзина дублей + предупреждение о связях

- Корзина уже реализована (`moveToTrash` стр. 525–537, `/trash`, `/restore`) — удалять дубли можно уже сейчас, новых эндпоинтов не нужно.
- Добавляем в бэкенд `GET /admin/customers/:id/links-count` (или расширяем ответ перед удалением): количество связанных deals/measurements/contracts/estimates-ссылок.
- Фронтенд: в подтверждении удаления показываем «К этой карточке привязано: договоров — N, замеров — N…». Если связей нет — обычное подтверждение; если есть — предупреждение с рекомендацией переприкрепить документы на основную карточку перед удалением (переприкрепление уже возможно штатно, как вы и сделали вручную).

## 3. Структурированный адрес + автосклейка

**Хранение** — новый ключ в JSON `extendedProfile.addressStructured`:
```ts
{ postalCode?, city, street, house?, building?, apartment? }
```
Старый `extendedProfile.address` (строка) остаётся источником для всех существующих потребителей (договоры, расчёты, замеры).

**Форма** (`CrmCustomerFormFields.tsx`, «Адрес проживания», стр. 419):
- вместо одного поля — 6 полей (индекс, город, улица, дом, корпус, квартира);
- автосклейка: при сохранении собираем строку «город, улица, дом N, корп. N, кв. N» (индекс опускаем в склейке для договоров, он нужен реже) и пишем оба значения: `addressStructured` + `address`;
- обратная совместимость: если у существующего заказчика есть только строка `address` — при открытии формы показываем старое поле как есть с пометкой; после первого редакактирования структура заполняется (без принудительного парсинга старых строк).

**Валидация** (`crmCustomerFormValidation.ts`): город и улица обязательны, если адрес заполняется; дом — опционально (сад/земля и т.п.).

**Потребители**: `applyCrmContractToForm.ts`, `packageDataTabCompletion.ts`, `estimateCrmCustomer.ts`, `measurementCrmCustomer.ts` продолжают читать `address`-строку — не трогаем; при необходимости отображения по частям добавим в `crmCustomerExtendedProfile.ts` геттер `getStructuredAddress`.

## Миграции
Не нужны: адрес в JSON, дубль-проверка на уровне запросов, `email @unique` уже есть (P2002 при равном email обрабатываем в ту же ConflictException с понятным сообщением).

## Порядок работ и проверка
1. Бэкенд: duplicate-check + проверки в create/update + links-count; юнит-тесты сервиса на сценарии (полное совпадение, однофамилец, разный телефон, удалённый дубль не мешает).
2. Фронтенд: duplicate-check в форме, модалка выбора «открыть существующего / создать всё равно», предупреждение при удалении со связями.
3. Структурированный адрес: форма + автосклейка + валидация.
4. Прогон: `npm test` в обоих пакетах, ручная проверка сценария из бага — создать дубль → система не даёт → существующая карточка открывается из подсказки.
