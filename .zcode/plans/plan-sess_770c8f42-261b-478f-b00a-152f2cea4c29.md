# Онлайн-собрания (видео-конференции) в админке — mesh WebRTC

## Контекст

Админам нужны встроенные онлайн-собрания. Выбор согласован: **mesh WebRTC** по образцу существующего модуля remote-help, **5–8 участников**, плюс демонстрация экрана, планирование через календарь и запись. База готова: socket.io за nginx (`/socket.io/` уже проксируется), WebRTC-сигналинг и ICE/TURN-конфиг в remote-help, роли/доступы, календарь-агрегатор, bell/push-уведомления. Пробелы: remote-help строго 1:1 (нет renegotiation, нет perfect negotiation, БД-запрос на каждый ICE-пакет), нет многопользовательских моделей.

## Ключевые решения

1. **Новый раздел `admin.meetings`** («Онлайн-собрания»): Nest-модуль + socket.io namespace `/meetings`. Remote-help не трогаем, кроме выделения общего ICE-хелпера.
2. **Mesh**: на клиенте `Map<userId, Peer>`, perfect negotiation (polite = лексикографически меньший userId, детерминированно с обеих сторон), renegotiation через `onnegotiationneeded`. Один исходящий видеотрек на участника (камера **или** экран через `replaceTrack`) + аудио — это держит аплоад в пределах 6–7 потоков.
3. **Лимиты**: жёсткий cap 8 участников (`MEET_MAX_PARTICIPANTS`, по умолчанию 8); при >4 пирах авто-деградация (320×240@12fps, maxBitrate ~300kbps через `sender.setParameters`) + подсказка выключить камеры; приоритет аудио.
4. **Сигналинг**: in-memory реестр `Map<meetingId, Map<userId, socketId>>` в gateway — проверка участия **без БД** на каждое сообщение (фикс узкого места remote-help). Один сокет на пользователя на собрание: повторный join выкидывает старый сокет (переключение вкладок).
5. **Запись локальная**: canvas-микс тайлов + WebAudio-микс аудио → MediaRecorder → скачивание `.webm` у записывающего. Серверной записи нет (нет SFU).
6. **Планирование**: `Meeting.scheduledAt` + нативный тип `meeting` в календаре-агрегаторе (у `CalendarEventDto` уже есть `href` → `/admin/meetings?join={id}`). Уведомления по паттерну waybill-notify: таблица `MeetingBellEvent` (bell-фид) + «reminder» за 15 мин до старта (вычисляется на лету при поллинге 60с — планировщик `@nestjs/schedule` не нужен) + web-push. Чат собрания — эфемерный, через socket, без БД.
7. **Доступ**: REST-префикс в `ADMIN_API_SKIPPED_PREFIXES` (роли/участие проверяет контроллер+сервис, как remote-help); ресурс `admin.meetings` дефолтно 6 ролям, у которых есть `admin.calendar`/`admin.messenger`: ADMIN, CONTENT_MANAGER, MODERATOR, SUPPORT, MANAGER, TECHNOLOGIST. SUPER_ADMIN — неявно. Участники собрания — любые активные ADMIN_ROLES.

## Этап 1 — БД и backend

**Prisma** (`backend/prisma/schema.prisma`, миграция `npx prisma migrate dev --name online_meetings`):
- `enum MeetingStatus { SCHEDULED ACTIVE ENDED CANCELLED }`
- `model Meeting`: id (cuid), title, description?, scheduledAt?, startedAt?, endedAt?, status, createdById → User (Restrict), createdAt; `@@index([status, scheduledAt])`
- `model MeetingParticipant`: meetingId (Cascade), userId (Cascade), joinedAt?, leftAt?, `@@unique([meetingId, userId])`
- `model MeetingBellEvent`: userId, meetingId, kind ('created'|'reminder'|'started'), title, message, href, createdAt
- Обратные relation-поля на User (как у remote-help, schema.prisma:237–238)

**Модуль `backend/src/admin/meetings/`** (по образцу remote-help):
- `meetings.controller.ts` — `@Controller('admin/meetings')`, `@UseGuards(JwtAuthGuard, RolesGuard)`, `@Roles(...ADMIN_ROLES)`, throttle на мутациях:
  - `POST /` создать { title, description?, scheduledAt?, participantIds[] } (валидация: активные ADMIN_ROLES, cap 8, автор — авто-участник) → bell+push участникам
  - `GET /` список (upcoming/past), `GET /my`, `GET /:id` (с участниками)
  - `PATCH /:id` (автор; пока SCHEDULED), `POST /:id/cancel` (автор)
  - `POST /:id/join` → проверка участия/статуса/лимита, первый join → ACTIVE+startedAt → `{ meeting, iceServers, peers }`
  - `POST /:id/leave` → leftAt; последний → ENDED
  - `GET /ice-servers`
- `meetings.gateway.ts` — namespace `/meetings`, JWT-handshake и `socketCorsOrigins()` (копия remote-help.gateway.ts:18–78); события:
  - C→S `meeting:join { meetingId }`: регистр в памяти, join в room `meeting:{id}`; ack `{ peers: userId[] }` вошедшему, `meeting:peer-joined { user }` остальным
  - C→S `meeting:signal { meetingId, toUserId, data }`: проверка по реестру → emit целевому сокету `meeting:signal { fromUserId, data }`
  - C→S `meeting:chat { meetingId, text }` / `meeting:media-state { mic, camera, screen }` → broadcast в room
  - disconnect: удаление из реестра, `meeting:peer-left { userId }`, `service.markLeft` (идемпотентно)
- `meetings.service.ts`, `dto/meetings.dto.ts`, `meetings.module.ts` (DatabaseModule, UsersModule, JwtModule async по `JWT_SECRET`, bell-push; регистрация в `backend/src/admin/admin.module.ts`)

**Общий ICE-хелпер**: `backend/src/common/lib/webrtc-ice.ts` (`getIceServersFromEnv()` из TURN_URL/TURN_USERNAME/TURN_CREDENTIAL + STUN Google) — используют и meetings, и remote-help (рефактор `remote-help.service.ts:290–305`).

## Ограничения и риски

- Mesh: комфортно 5–6, на 8 — деградация качества; при росте — LiveKit SFU (следующий шаг, архитектура Meetings это позволяет)
- Камера и экран одновременно не транслируются (одно видео на участника) — осознанное ограничение mesh
- TURN обязателен за симметричным NAT: coturn уже описан закомментированным в `docker-compose.infra.yml:46–59` — включить на проде при проблемах соединения
- Запись только локальная у участника; серверной записи без SFU нет
- Один инстанс backend (in-memory реестр) — соответствует текущей инфраструктуре (presence уже так работает)
- Повторяющиеся собрания не поддержаны (в проекте нет recurrence нигде) — при необходимости разворачивать в отдельные Meeting
