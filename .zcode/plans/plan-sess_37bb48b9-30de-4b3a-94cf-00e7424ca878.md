Правка логики оформления д/с и блокировок после подписания договора

# Контекст (установлено при диагностике)

Договор 77/3/1д-6 (DOORS, статус CONTRACT_CONCLUDED). Расчёты «двери допы»/«двери на минус» (dir=DOORS, «В работе», объект «Книповича 5-11», свободны) не попадают в выпадающие списки д/с по двум причинам:

1. У пакета пуст `estimateObjectGroupKey` и к «Счёт-заказу» не прикреплён ни один расчёт → `attachableAddendumEstimatePresets` сразу возвращает `[]` (usePackageEstimateAttachCatalog.ts:249-250), селекты дизейблены («— сначала счёт-заказ договора —»).
2. В formData нет `_linkedCrmCustomerId` — данные заказчика попали в форму через анкету, а привязка через «Поиск заказчика в базе» не выполнялась/не сохранилась. Для товарных направлений фильтр по заказчику включён всегда → без привязки не показывается ни один расчёт. После подписания вкладка «Данные» заблокирована → привязать из UI нельзя.

Целевые правила заказчика: (1) привязка пакета — на «Данных»; (2) для Дверей/Окон/Потолков/Жалюзи достаточно Спецификации ИЛИ Счёт-заказа; (3) после подписания блокируются только Спецификация и Счёт-заказ (в Ремонте — только Смета), д/с не блокируется до закрытия договора.

# Изменение 1. Новая семантика блокировок

В `usePackageDocumentEditorController.ts` (стр. 209-212) заменить один флаг `contractAndEstimateLocked` на два:

- `signedDocsLocked = status === 'CONTRACT_CONCLUDED' || status === 'REFUSED'` — блокирует «Счёт-заказ»/«Смету», «Спецификацию» и подсказку д/с до подписания;
- `packageReadOnly = status === 'REFUSED'` — полная блокировка всего остального (только «Отказ»).

Все ~30 потребителей `contractAndEstimateLocked` перевести на один из двух флагов (механический ренейм, контроль через type-check):

Оставить на `signedDocsLocked` (поведение не меняется):
- «Счёт-заказ»/«Смета»: PackageEstimateTabView, PackageEstimateAttachPanel, PackageEstimateTab + хук `usePackageEstimatePresetHandlers` (ранний выход applyEstimatePresetIdsToForm);
- «Спецификация»: инъекция `disabled` в PackageDocumentEditorTabContent.tsx:288 (сегодня туда идёт contractAndEstimateLocked — семантика та же);
- иконки-замки в TabBar (PackageDocumentEditorTabBar.tsx:77-82) — только для вкладок estimate и specification (у product-like), с вкладки «Договор» замок убрать;
- `lockedHint` д/с в usePackageAddendumEditor.ts:322-325 (условие «не подписан» = !signedDocsLocked — сохраняет текущее поведение: до подписания вместо блока подсказка).

Перевести на `packageReadOnly` (после подписания разблокируется):
- Вкладка «Данные» целиком: PackageDataContractObjectSection (номер/офис/замерщик/дата/срок/скидка/объект/исполнитель/менеджер), PackageContractNumberField, PackageDataCustomerSearchColumn (панель «Поиск заказчика в базе»), бейджи-замки секций, PackageDataTabView/PackageDataTab;
- хуки: `usePackageProfileDirectoryHandlers` (ранние выходы handleCrmCustomerApplied/Clear, applyExecutorProfile/applySignatoryProfile), `usePackageContractFieldHandlers` (блокировка updateObject/updateContract — белый список PACKAGE_CONTRACT_FIELDS_EDITABLE_WHEN_SIGNED становится не нужен, использование убрать), `usePackageContractObjectBlockUi` (серые поля), `usePackageDataTabFieldHelp` (тексты подсказок);
- вкладка «Договор» (шаблон): убрать lock-нотис в PackageTemplateEditorPane.tsx:34-36 (богатый редактор шаблона смонтирован не везде — там, где используется useContractTemplateEditor.ts:71, тоже перевести на packageReadOnly);
- прогон флага через агрегаторы: usePackageDocumentEditorUiProps, usePackageDocumentEditorTabProps (dataTabProps), usePackageDocumentEditorTabContentShellProps, PackageDocumentEditorMainView, PackageDocumentEditorChrome.

Решения по умолчанию (вопросы пользователь пропустил): «Мебель» не входит в перечисленные направления — её специфичные вкладки (Заказ-наряд, Накладная, монтажная смета в TabContent:188/239/256/270) остаются на текущей полной блокировке после подписания; «Данные» после подписания разблокируются целиком (буквальное прочтение правила). Обе позиции легко скорректировать одним флагом.

# Изменение 2. Объект д/с без прикреплённого Счёт-заказа

Чтобы д/с работало для договоров «только со Спецификацией» (правило 2):

Использовать его в `attachableAddendumEstimatePresets` (замена `objectKey`) и вернуть наружу для лейбла;

Суммы основного договора это не трогает;
- `usePackageAddendumEditor.ts`: `contractEstimateObjectLabel` и `applyAddendumPresetIds` переключить на переданный из каталога `addendumEstimateObjectKey`.

После этого для 77/3/1д-6: адрес «Книповича 5-11» → группа grp_1788430912826_l2ywfu → списки д/с начнут заполняться сразу после привязки заказчика.

# Изменение 3. Привязка заказчика (кода почти не требует)

Следствие изменения 1: после подписания «Поиск заказчика в базе» на «Данных» активен → пользователь заново применяет карточку Сидоркина → `_linkedCrmCustomerId` сохраняется (buildPersistedFormData) → фильтр заказчика в д/с начинает пропускать его расчёты. Патч БД не нужен, БД не трогаем.

# Что НЕ меняется

- Блокировка отдельных слотов д/с при их собственном SIGNED/PAID (с окном отката) — это жизненный цикл каждого д/с;
- подсказка «Прикрепление расчётов к доп. соглашению доступно после статуса „Договор подписан"» до подписания — д/с логично существует только для подписанного договора;
- REFUSED: полная блокировка + запрет persist (usePackageDocumentPersist) — как сегодня;
- бэкенд: без изменений (валидация assertPipelineActive для этих расчётов проходит: направление DOORS, «В работе», не архив).
