# Доработка ПЭП: штампы на PDF, протокол подписания, хранение подписанного комплекта

## Контекст (что подтверждено кодом)
Подписание работает корректно на уровне аудита (OTP-хэш, IP/UA, таймстемпы, снимок версии), но: (1) PDF уходят клиенту без отметки со стороны Подрядчика; (2) после подписания файлы остаются неизменными — без штампа о факте ЭП; (3) единого «подписанного комплекта» нет, а «Скачать PDF» в модалке шеринга перегенерирует документы из текущих данных (риск расхождения с подписанной версией).

Решения пользователя: штамп клиента на последней странице каждого PDF + лист-протокол; текстовая серверная отметка ПЭП Подрядчика при отправке; единый PDF-комплект; SHA-256 хэши документов; письмо клиенту с комплектом после подписания. Без ZIP, без сканов подписи/печати, без кнопки скачивания на публичной странице.

Оригиналы файлов (что видел клиент) не перезаписываются после подписания — штампованные копии пишутся рядом, это доказательная база.

## 1. Зависимости и шрифты (backend)
- `npm install pdf-lib @pdf-lib/fontkit`.
- Добавить в репозиторий `backend/assets/fonts/Roboto-Regular.ttf` и `Roboto-Bold.ttf` (OFL-лицензия, скачать с Google Fonts) — стандартные шрифты pdf-lib не поддерживают кириллицу.

## 2. Prisma-миграция
Новые nullable-колонки в `ContractDocumentSigningSession` (schema.prisma:3803):
- `contractorLabel` — реквизиты Подрядчика для штампа («ООО «…», ИНН …»);
- `contractorSignatory` — подписант со стороны Подрядчика (ФИО + основание);
- `signedPackageUrl` — путь к единому PDF подписанного комплекта.
Поля `sha256` и `signedFileUrl` добавляются внутрь существующего `documents` JSON — миграция не нужна.

## 3. Новый сервис `backend/src/contract-document-signing/signing-stamp.service.ts`
- `drawStampBlock(pdfDoc, lines)` — блок в духе Сбербанка: полупрозрачная белая плашка с рамкой внизу последней страницы, текст Roboto (время в «Europe/Moscow», формат `dd.MM.yyyy HH:mm МСК`).
- `stampContractorSide(buffer, ctx)` — «Документ направлен на подписание и подписан простой электронной подписью со стороны Подрядчика: {contractorLabel}. Подписант: {contractorSignatory}. Дата/время: {…}. Сессия ЭП №{id.slice(0,8)}».
- `stampCustomerSide(buffer, ctx)` — «Подписано простой электронной подписью (ПЭП): {signedName}. Дата/время подписания: {…}. Договор: {title}. Сессия ЭП №{…}».
- `buildProtocolPage(ctx)` — лист-протокол: реквизиты договора, заказчик и подписант, таблица документов (название, файл, SHA-256, отметка «направлен в исходном виде» для не-PDF), события (отправка/просмотр/подписание с датами), ссылка на п. 7.5–7.10 договора, IP/UA подписания.
- `buildSignedPackage(...)` — склейка [протокол] + все штампованные PDF в один файл.
- Не-PDF внешние файлы (RTF и пр.) не штампуются — попадают только в протокол с хэшем.

## 4. Изменения `contract-document-signing.service.ts`
- `persistSigningSessionDocuments` (signing-session-documents.ts): для каждого PDF сразу после записи — штамп Подрядчика, затем sha256 финального буфера в meta (клиент по ссылке видит уже проштампованную версию).
- `createSession`: принять multipart-поля `contractorLabel`, `contractorSignatory` от фронтенда (фронт уже сопоставляет профиль реквизитов и подписанта); fallback — глобальные реквизиты исполнителя для kind пакета; сохранить в сессию.
- `sign()`: после успешной фиксации подписи — `finalizeSignedSession()` в try/catch (ошибка штампов не должна ломать фиксацию подписи): штамп клиента на каждый PDF → `uploads/contract-document-packages/signing/{sessionId}/signed/{i}_{tab}_signed.pdf`, сборка единого `…_{номер или id}_signed_package.pdf`, обновление `signedPackageUrl`/`signedFileUrl` в `documents`, отправка письма клиенту с вложением.
- `finalizeSession(packageId, sessionId)` — идемпотентная (пере)генерация для админки: работает и для легаси SIGNED-сессий (обратная сила — просто генерирует комплект из сохранённых оригиналов).
- `sendSignedPackageEmail`: тема «Документы подписаны», текст (ФИО, дата/время, перечень), вложение PDF (nodemailer `attachments`); ошибка — только лог.
- `toAdminDto` и `getPublicSession`: отдавать `signedFileUrl`/`signedPackageUrl` (на публичной странице кнопку скачивания не добавляем).

## 5. Admin-контроллер `contract-document-signing-admin.controller.ts`
- `POST admin/contract-document-packages/:packageId/signing-sessions/:sessionId/finalize` (те же роли) — принудительная (пере)генерация, возвращает обновлённую сессию.

## 6. Frontend
- `shared/api/contract-documents/admin-contract-document-signing.ts`: типы (`signedPackageUrl`, `signedFileUrl`, `sha256`), функция `finalizePackageSigningSession()`.
- `PackageRemoteSigningModal.tsx`: передать в запрос `contractorLabel` (из сопоставленного `ExecutorRequisiteProfile`: companyName/title + ИНН) и `contractorSignatory` (из `ContractSignatoryProfile`: directorNameNominative + basis).
- `PackageRemoteSigningTimeline.tsx`: для SIGNED-сессий кнопка «Скачать подписанный комплект (PDF)» — если `signedPackageUrl` нет, сначала вызвать finalize (лениво, покрывает легаси), затем открыть файл; ссылки на документы ведут на штампованные версии с пометкой, оригинал доступен рядом.

## 7. Формулировки договоров (задача пользователя, не кода)
Рекомендую дополнить раздел 7 шаблонов: пункт о том, что на Электронные документы наносится визуальная отметка (штамп) о подписании ПЭП с датой и временем, формируется протокол подписания, подписанный комплект хранится на Сайте, а волеизъявление Подрядчика фиксируется отметкой при отправке. Шаблоны редактируются в админке.

## 8. Тесты и валидация
- Spec на `signing-stamp.service` (штамп наносится, PDF валиден, кириллица читается, merge, идемпотентность finalize) и на обновлённые пути service (sha256 в meta, contractor-поля).
- `npm run validate` в backend; type-check/lint frontend.
- Ручная проверка: создать сессию → в PDF виден штамп Подрядчика; подписать → штамп клиента, протокол, единый PDF, письмо с вложением; для старой SIGNED-сессии → «Скачать подписанный комплект» генерирует комплект по кнопке.
